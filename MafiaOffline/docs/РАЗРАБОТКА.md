> Удобные условия для работы в GitHub: структура, CI, релизы, quality gates.
> Корень Flutter-проекта — папка `MafiaOffline/` (здесь и запускаются команды).
> Матрица требований: [`ТРАССИРУЕМОСТЬ.md`](ТРАССИРУЕМОСТЬ.md).

## 1. Быстрый старт разработчика

### Требования

| Инструмент | Версия | Зачем |
|---|---|---|
| Flutter | 3.24.5 (stable) | Сборка APK, тесты |
| JDK | 17 (Temurin) | Gradle (Java 25 ломает сборку — см. `ОШИБКА_СБОРКИ.md`) |
| Python | 3.11+ | Стенды `tools/` |
| Node.js | 20+ | Проверка синтаксиса веб-клиента |
| Android SDK | API 34–35 | Сборка APK |

### Команды (из папки `MafiaOffline/`)

```bash
flutter pub get
flutter analyze        # статический анализ
flutter test           # юнит-тесты Dart
python3 tools/demo20.py    # демо-партия на 20 игроков
python3 tools/stress.py    # 400 партий, инварианты
python3 tools/winrule.py   # правило победы мафии
python3 tools/edge.py      # пограничные сценарии
python3 tools/forcestart.py # принудительный старт
node --check assets/web/app.js && node --check assets/web/sw.js
flutter build apk --release   # APK: build/app/outputs/flutter-apk/app-release.apk
```

> На машине с 8+ ГБ ОЗУ поднимите лимиты в `android/gradle.properties`
> (`-Xmx3g`, `daemon=true`) — сборка ускорится в разы. В CI это делается
> автоматически (см. `.github/workflows/release.yml`).

### CI (GitHub Actions)

- `.github/workflows/ci.yml` — при каждом push/PR в `main`:
  `flutter analyze` + `flutter test` + Python-стенды + проверка JS.
- `.github/workflows/release.yml` — при теге `v*`: сборка APK (universal + arm64)
  и публикация GitHub Release.

Merge только при зелёном CI (PR Gate).

## 2. Структура и где что лежит

```
MafiaOffline/            ← корень Flutter-проекта
├── lib/                 ← Dart: core, models, net, host, player, services, storage, ui
├── assets/web/          ← веб-клиент (index.html, app.js, style.css, sw.js)
├── assets/cards/        ← карты ролей (+ web/ — лёгкие версии для браузера)
├── assets/sounds/       ← звуки (+ web/ — лёгкие лупы)
├── android/ ios/        ← платформенные обёртки
├── test/                ← Dart-тесты
├── tools/               ← Python-стенды (engine.py — порт логики)
├── docs/                ← документация (этот файл, ТРАССИРУЕМОСТЬ, CHANGELOG, ...)
├── apk/                 ← локальные APK (в git НЕ коммитятся)
└── keystore/            ← ключ подписи (в git НЕ коммитится)
```

Ключевые файлы:

| Файл | Роль |
|---|---|
| `lib/core/game_engine.dart` | Чистая игровая логика (раздача, ночь, победа) |
| `lib/host/host_controller.dart` | Ведущий: фазы, таймеры, рассылка (источник истины) |
| `lib/net/host_server.dart` | HTTP :8088 + WebSocket /ws |
| `lib/net/protocol.dart` | Формат пакетов (JSON, `v`, `ts`) |
| `lib/net/web_assets.dart` | Раздача статики (Gzip, ETag, LRU) |
| `assets/web/app.js` | Веб-клиент игрока (паритет с `player_controller.dart`) |
| `pubspec.yaml` | Версия (`1.0.5+5`), зависимости, ассеты |

## 3. Регламент полного цикла (по ТЗ заказчика)

### 3.1. Принципы

- **Трассируемость:** каждое требование ТЗ → задача → тест → код → приёмка.
  ID требований — в [`ТРАССИРУЕМОСТЬ.md`](ТРАССИРУЕМОСТЬ.md) (`FR-*`, `AF-*`, `BR-*`, `NFR-*`, `AC-*`).
- **Итерационность:** сначала MVP/критичный контур, затем расширение.
- **Quality Gates:** без прохождения гейтов задача не считается выполненной.
- **Никаких неучтённых допущений:** неясно → уточняем или фиксируем в журнале допущений.
- **Человеческое подтверждение** для критичных решений: прод-деплой, миграции БД,
  безопасность, архитектурные развилки (ADR).

### 3.2. Роли (ИИ-агент выполняет последовательно)

PM/владелец (приоритеты, приёмка) → BA (требования, критерии) → TL/архитектор
(решения, ADR) → разработчик (код, тесты, docs) → QA (тест-план, регресс) →
DevOps (CI/CD, релизы) → Security (секреты, доступы) → TechWriter (docs, changelog).
На критичных гейтах — остановка на подтверждение человека.

### 3.3. Цикл по ТЗ

| Этап | Действия | Выход | Критерий завершения |
|---|---|---|---|
| 0. Приём ТЗ | Регистрация ТЗ, цели, ФР/НФР, ограничения, приёмка | Реестр требований, журнал вопросов/рисков | ТЗ разобрано, пробелы выявлены |
| 1. Анализ | Матрица трассируемости, эпики/задачи, MVP, архитектура, CI/CD, тест-стратегия | Backlog, roadmap, test plan, release plan | Задачи имеют DoR, приоритет, оценку |
| 2. Проектирование | Модули, API/протокол, модель данных, UI/UX, ошибки, логи, безопасность | Design docs, контракты, threat model | Ревью TL/Security пройдено |
| 3. Реализация | Ветка, минимальное изменение, unit/integration-тесты, docs, локальные проверки, PR | Код, тесты, docs, PR | PR содержит требование и тесты |
| 4. Ревью и CI | Линтеры, сборка, тесты, SAST, scan; peer/TL review; merge при зелёном CI | Merged code, запись ревью | Все проверки пройдены |
| 5. Тестирование | Функциональное, регрессионное, интеграционное, совместимость; UAT | Test reports, defects, acceptance | Критичных дефектов нет |
| 6. Релиз | Release candidate, changelog, версионирование, runbook, rollback; smoke | Release notes, deployment log | Прод проверен |
| 7. Сопровождение | Мониторинг, инциденты, обратная связь, RCA | Incident reports, backlog | Инциденты управляются |
| 8. Закрытие | Сверка с ТЗ, акт приёмки, архив, retro | Acceptance act, архив | Все требования закрыты/перенесены |

### 3.4. Алгоритм агента (кратко)

1. Прочитать ТЗ и приложения; присвоить требованиям ID (уже в `ТРАССИРУЕМОСТЬ.md`).
2. Сформировать/обновить матрицу «требование → задача → тест → артефакт».
3. Проверить DoR; при пробелах — вопросы или зафиксированное допущение.
4. Выбрать следующую задачу по приоритету и зависимостям.
5. Спланировать изменение: файлы, тесты, риски, влияние.
6. Реализовать в отдельной ветке; локальные проверки.
7. PR по шаблону (`.github/pull_request_template.md`).
8. CI; исправить ошибки; пройти ревью.
9. Merge только после зелёного CI и approvals.
10. Релиз по runbook; smoke-проверка.
11. Обновить docs, changelog и матрицу трассируемости.
12. Отчитаться: сделано / заблокировано / следующий шаг.

### 3.5. Quality Gates

- **DoR:** понятно требование, критерии приёмки, зависимости, оценка, тест-подход.
- **PR Gate:** CI зелёный, ревью пройдено, тесты есть, секретов нет, трассируемость есть.
- **Release Gate:** тесты и UAT пройдены, rollback готов, мониторинг настроен.
- **DoD:** код + тесты + docs + ревью + CI + трассируемость + нет критичных дефектов.

### 3.6. Правила и запреты

- Не выдумывать требования; неясное — в журнал вопросов/допущений.
- Не обходить CI, ревью и quality gates.
- Маленькие изменения и атомарные PR (одно требование — один PR).
- Не хранить секреты и PII в коде/логах (см. `.gitignore`: `*.keystore`, `key.properties`, `.env`).
- Критичные решения — в ADR (журнал в `ТРАССИРУЕМОСТЬ.md`).
- Останавливаться на подтверждение человека перед прод-деплоем, миграциями, security.
- При падении тестов — исправить или явно сообщить о блокере.

### 3.7. Формат отчёта агента

`Статус: сделано/в работе/заблокировано. Требование: ID. Изменения: ... Тесты: ... CI: ... Риски: ... Следующий шаг: ...`

## 4а. Известные места, куда смотреть при доработке

Короткий список «где что лежит» — чтобы не искать по 1100 строк `HostController`:

| Что нужно | Где |
|---|---|
| Раздача ролей и гейт первой ночи | `HostController.startGame()`, `_handleRoleAck()`, `skipRoleCheck()` |
| Фазы и их названия | `models/game_phase.dart` (единственное объявление `GamePhase`) |
| Возврат игрока в свой слот | `HostController._handleRegister` (опознание **до** проверки фазы) |
| Переименование | `HostController.renamePlayer(..., allowDuringGame:)` |
| Повторный показ роли | `HostController.reshareRole()` |
| Цвета игроков | `constants.dart: colorForSlot()` |
| Сохранение партии | `storage/session_store.dart` (фаза `rolesCheck` сохраняется как есть) |
| Веб-клиент | `assets/web/app.js`, `assets/web/index.html`, `assets/web/style.css` |
| Что клиент получает после переподключения | `HostController._syncEnvelopeFor` (в т.ч. `roleAck`) |

**Правило протокола.** Новый тип пакета или новое поле в существующем — это
изменение контракта. Оно требует:

1. записи в `docs/ТРАССИРУЕМОСТЬ.md` (журнал допущений/ADR);
2. изменения **и** в Dart-клиенте, **и** в `assets/web/app.js`;
3. теста в `test/` на разбор пакета (`Envelope.decode`).

Новые поля добавлять безопасно: `Envelope.get<T>()` возвращает `null` для
отсутствующего ключа. **Удалять и переименовывать** поля без смены
`Net.protocolVersion` нельзя — старый веб-клиент из кэша перестанет понимать
сервер. И помните: при несовпадении версии `Envelope.decode` **молча**
отбрасывает пакет, поэтому клиент при этом просто «висит» — диагностировать
такое тяжело (см. `РЕКОМЕНДАЦИИ_РАЗРАБОТЧИКА.md`, п. 3.2).

## 5. Релиз и подпись

### 5.1. Версионирование

- Версия в `MafiaOffline/pubspec.yaml`: `version: 1.0.5+5`
  (`versionName` — человекочитаемая, `versionCode` — монотонно растёт).
- Без увеличения `versionCode` Android не обновит установленное приложение.
- Тег GitHub: `v<versionName>` (например, `v1.0.6`).

### 5.2. Чек-лист релиза

1. Поднять версию в `pubspec.yaml` (`1.0.5+5` → `1.0.6+6`).
2. Добавить `docs/CHANGELOG_<версия>.md`.
3. Если менялись `assets/web/`, `assets/cards/web/`, `assets/sounds/web/`:
   - поднять `WebAssets.assetVersion` в `lib/net/web_assets.dart`;
   - поднять `VERSION` в `assets/web/sw.js`.
4. Проверить паритет протокола: `assets/web/app.js` ↔ `lib/player/player_controller.dart`,
   `V = 1` ↔ `Net.protocolVersion = 1`.
5. Прогнать CI (зелёный).
6. Создать тег и запушить: `git tag v1.0.6 && git push origin v1.0.6`.
7. Воркфлоу `release.yml` соберёт APK и опубликует GitHub Release.
8. Smoke-проверка: установить APK ведущего, прогнать партию на 2+ устройствах.

### 5.3. Подпись (важно!)

- Сейчас `android/app/build.gradle` подписывает релиз **debug-ключом**
  (`signingConfig = signingConfigs.debug`). Это работает для тестов,
  но для продакшена нужен **релизный keystore**.
- Текущий ключ: `keystore/debug.keystore`
  (SHA-256 `117b5d7eb24ec6e183bc62088fdc452db4b5cee4d8327ef7f7ffabae8c9b6dff`).
  В git не коммитится (`.gitignore`). Храните резервную копию отдельно —
  без него нельзя выпустить обновление поверх установленной версии.
- Для релизного ключа:
  1. Сгенерировать: `keytool -genkey -v -keystore mafia-release.jks -keyalg RSA -keysize 2048 -validity 10000 -alias mafia`.
  2. Положить в GitHub Secrets: `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`.
  3. Создать `android/key.properties` (не коммитить!) и настроить `signingConfigs.release`
     в `android/app/build.gradle`.
  4. Обновить воркфлоу `release.yml` (шаг восстановления keystore из секретов).
- **Смена ключа = смена подписи:** пользователи не смогут обновиться поверх
  старой версии без удаления. Планируйте переход заранее и сообщайте в release notes.

### 5.4. GitHub Releases

- APK в git не коммитятся. Распространение — только через GitHub Releases.
- Релиз `v1.0.5` уже опубликован с архивными APK (см. вкладку Releases).
- Новые релизы создаются автоматически воркфлоу при теге `v*`.
