# Рекомендации разработчика: что делать дальше и почему

> Документ для владельца продукта и следующего разработчика. Здесь нет
> пересказа кода — только решения, которые стоит принять, и их цена.
> Состояние на v1.0.5+5 (после доработок по `OPEN_QUESTIONS.md`).
>
> Порядок — по соотношению «польза / риск». Всё, что помечено **P0**,
> имеет смысл сделать до следующего релиза.

---

## 0. Главное, что я бы изменил в процессе (не в коде)

**CI должен быть зелёным на `main`, иначе он не работает.**
PR #1 был красным: `flutter analyze` находил 4 замечания, но в логах GitHub
видно было только «exit code 1». Пока анализатор красный, никто не смотрит
на новые предупреждения — и через месяц их станет двести.

Что сделано: в `.github/workflows/ci.yml` добавлен шаг, который при падении
`flutter analyze` выкладывает вывод в PR комментарием. С его помощью
замечания найдены и устранены; сейчас CI зелёный полностью. Дальше — одно
правило: **PR не мержится, пока не зелёный**, и это стоит закрепить в
branch protection (см. §6 руководства разработчика).

**Версию поднимать в каждом PR, который меняет поведение.**
`pubspec.yaml: version: 1.0.5+5`. Сборка `release.yml` берёт версию оттуда.
Если забыть — два разных APK называются одинаково, и на телефоне ведущего
непонятно, что установлено.

**Не копить «мелкие правки» в одной ветке.**
Изменение протокола (например, `deviceId`) и текст подсказки в лобби — разные PR.
Иначе откатить одно, не откатив другое, невозможно.

## 1. P0 — надёжность, которую не видно на демо

### 1.1. ~~`reconnectAttempts = 3` слишком мало~~ ✅ сделано

`constants.dart` — три попытки с паузой 2 секунды, дальше `ConnStatus.failed`
и экран «Не удалось переподключиться». В вебе давно сделано правильно:
неограниченные попытки с растущей паузой и случайным разбросом. Нативный клиент
сдаётся через 6 секунд.

**Почему это важно:** на телефоне ведущего включена точка доступа на 8–20
устройств. Роуминг, засыпание экрана, переключение 2.4/5 ГГц — обычное дело.
Игрок, у которого нативный APK, потеряет партию там, где браузерный сосед
вернётся сам.

**Что сделать:** привести `ClientConnection._handleDrop` к веб-логике:
цикл до `dispose()`, пауза `min(400ms * 1.6^n, 8s) + random(0..600ms)`,
кнопка «Повторить» остаётся для ручного ускорения. Оценка: ~30 строк,
тесты — существующие `resilience.py` не покрывают Dart, нужен widget-тест
с фиктивным сокетом.

### 1.2. ~~Таймер ночи короче, чем нужно~~ ✅ сделано

`nightBaseSeconds = 20`, `nightPerActiveSeconds = 10`. При 3 активных ролях —
50 секунд. Это нормально для третьего раунда и мало для первого: люди ещё
читают памятку, ищут кнопку, выбирают.

**Рекомендация:** первый раунд — множитель 1.5 (или `nightBaseSeconds = 30`
только для раунда 1). Правка в `GameState.nightDuration`: `round == 1 ? base*1.5 : base`.
Дешево, снимает самый частый раздражитель.

### 1.3. ~~Новая партия молча затирает сохранение~~ ✅ сделано

Если ведущий создал новую партию, не восстановив старую, `SessionStore`
перезапишется — старая партия молча пропадёт. Это правильное поведение,
но **пользователь об этом не знает**: он видит «Есть незавершённая партия»
и кнопку «Новая игра» рядом.

**Что сделать:** в диалоге создания партии, если есть сохранение, писать
явно: «Текущая незавершённая партия будет удалена». Одна строка, снимает
целый класс обращений «куда делась игра».

## 2. P1 — то, что даст больше всего пользы за вечер

### 2.1. ~~Экспорт протокола партии~~ ✅ сделано (FR-7.7)

`history_repository.dart` хранит партию целиком, `history_screen.dart` умеет
показать. Не хватает «Поделиться» — `share_plus` или просто
`Clipboard.setData` + `Share.share` текстом.

**Зачем:** это единственный способ разобрать спорный момент после игры
(«кто кого выгнал в третьем раунде»), и он же закрывает слабое место из
`OPEN_QUESTIONS` 5.1 — не нужно передавать роль ведущего, достаточно
сохранить протокол.

### 2.2. ~~Настройка «стартовать ночь сразу»~~ ✅ сделано

Гейт из вопроса 2 — правильный по умолчанию, но компания, играющая каждую
неделю, читает роли за 5 секунд и не хочет ждать прогресс-бар.

**Что сделать:** `AppPrefs` уже есть. Добавить `autoStartNight` (по умолчанию
`false`): если все подтвердили — ночь начинается сама (как сейчас); если
выключено — ведущий жмёт «Начать ночь» вручную, а панель показывает «Все
готовы». Осторожно: это **не** отменяет гейт, а меняет только автозапуск.

### 2.3. ~~Пресеты состава не проверяются на баланс~~ ✅ сделано

`setup_screen.dart` предупреждает, если мафия ≥ ½. Но пользовательский пресет
из `AppPrefs` может быть сохранён в старой версии, где проверки не было.
Сейчас он загрузится молча.

**Что сделать:** одну функцию `validateSetup(setup, players)` в `GameEngine`
и вызывать её и для пресета, и для ручных счётчиков. Сейчас логика проверки
размазана по UI — это будущий источник расхождений.

## 3. P2 — архитектурный долг, который стоит платить заранее

### 3.1. `HostController` — всё ещё большой ⚠️ частично

Внутри: приём сообщений, регистрация, лобби, раздача, ночи, дни, голосование,
таймеры, звук, сохранение, история. Это работает, но каждое новое правило
(гейт ролей, повторный показ роли) добавляет ветку в тот же файл.

**Рекомендация (без переписывания):** вынести чистые функции решения в
`GameEngine` (`GameState + действие → GameState + список событий`), оставив в
контроллере только ввод-вывод. Первый кандидат — `_handleRoleAck` и
`skipRoleCheck`: они уже почти чистые. Это даст возможность покрыть их
обычными unit-тестами без сервера.

**Чего делать НЕ надо:** переписывать на Riverpod/Bloc. `ChangeNotifier` здесь
работает; проблема не в управлении состоянием, а в размере одного класса.

### 3.2. ~~Протокол без версионирования по полям~~ ✅ сделано

`Envelope` несёт `v: 1` и **отбрасывает пакет целиком**, если версия не совпала.
Значит, любое добавление поля требует, чтобы у всех игроков была одна версия
страницы. В вебе спасает `sw.js` с `skipWaiting`, но кэш на телефоне может
отдать старую страницу.

**Рекомендация:** при несовпадении версии отправлять клиенту `register_denied`
с `bad_version` и текстом «Обновите страницу» — сейчас клиент молча висит.
Правка на 5 строк, снимает самый загадочный класс «не подключается».

### 3.3. ~~Нет ни одного теста на `HostController`~~ ✅ частично (правила ролей вынесены)

Есть `game_engine_test.dart` (хороший), `wifi_qr_test.dart`, `widget_test.dart`
(два теста про меню). Логика регистрации, возврата в слот и подтверждения ролей
не покрыта ничем — а это как раз то, что ломалось в v1.0.4.

**Рекомендация:** `HostController` создаётся без сервера? Нет — сервер стартует
в `createGame`. Вынести `_handleRegister` и `_handleRoleAck` в чистые функции
(см. 3.1) и покрыть их тестами. Это дешевле, чем поднимать fake-сервер.

## 4. Чего я бы не делал

| Идея | Почему нет |
|---|---|
| Передача роли ведущего на второе устройство | Второй сервер, который всё время молчит; сложно и редко нужно (см. OPEN_QUESTIONS 5.1) |
| Ручная правка роли игроку | Ломает баланс и историю; правильный ответ — «перезапуск с тем же составом» (5.4) |
| Хранение состояния на сервере/в облаке | Противоречит NFR-10 (данные не покидают устройства) и всей идее офлайн-игры |
| Замена `ChangeNotifier` на «модный» state manager | Нет проблемы, которую это решает; риск больше пользы |
| Блокировка старта из-за коротких имён | Один «Ян» остановит весь стол; предупреждения достаточно (вопрос 1) |
